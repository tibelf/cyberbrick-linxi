# CyberBrick 语音坦克 — 技术方案

> 课题：七牛 Hackathon「智能硬件」：做一款能发子弹的小车，接入灵矽（Linx）实现语音交互。
> 目标：对小车说「往前走两秒，左转，开一炮」，小车照做并用语音回应；说「停」立刻停车。
> 状态：已实车跑通（电脑模拟灵矽设备 + Wi-Fi 控车）。
>
> 本文讲协议和实现细节。总体架构、模块职责和主打场景见 [架构设计](架构设计.md)，怎么跑起来见 [运行说明](运行说明.md)。

---

## 1. 方案选择

| 项 | 结论 |
|---|---|
| 小车 | CyberBrick Mini T 履带车 + 顶部发射器，主控 Core = ESP32-C3（MicroPython），有 USB 口 |
| 语音 / 大模型 | 灵矽平台：ASR → 大模型（Function Call）→ TTS；智控台 `xrobo.qiniu.com` |
| 灵矽设备 | 没有实体硬件，由电脑上的 `linx-client`（Python）模拟：电脑麦克风 + 扬声器 |
| 控车 | 主用 Wi-Fi UDP（车上装 `firmware/car/wifi_main.py`）；USB 串口 raw REPL 作为有线调试 |
| 参考 | [qiniu/Xrobot-docs](https://github.com/qiniu/Xrobot-docs)、[linx-linux 客户端示例](https://github.com/sunqirui1987/linx-linux) |

**做过但放弃的方向**：曾计划让安卓手机网页直接当灵矽设备，通过 WebUSB 或蓝牙控车（2026-10-23）。后来确认车有 USB 口、Wi-Fi UDP 链路更简单可控，网页版没有实施，主线回到 `linx-client`。

## 2. 灵矽接入流程

1. **OTA 激活**：`POST https://xrobo.qiniuapi.com/v1/ota/`，携带虚拟 MAC（`Device-Id`）和 UUID（`Client-Id`）。未绑定时平台返回 6 位激活码，在智控台绑定后再次上报，拿到 `websocket.url` 和 `token`。身份保存在 `.linx_device.json`，不进仓库。
2. **WebSocket 连接**：OTA 下发 `ws://xrobo-io.qiniuapi.com/v1/ws/`（`wss://` 也可用）。握手请求头带 `Authorization: Bearer <token>`、`Device-Id`、`Client-Id`、`Protocol-Version: 1`。
   - 实测平台**只认 Device-Id、不校验 token**，所以 Device-Id 就是唯一凭据，绝不能写进仓库。代码仍然带上 token，平台收紧鉴权后不用改。
3. **hello**：上行声明 PCM 16kHz/16bit/单声道/20ms，同时声明 `features.mcp = true`。下行格式以服务端 hello 为准，实测也是 PCM 16kHz，不需要 opus。
4. **MCP**：平台依次发 `initialize` → `tools/list` → `tools/call`，消息格式 `{"type":"mcp","payload":<JSON-RPC 2.0>}`。`initialize` 的 `capabilities.vision` 里带视觉接口的 `url` 和 `token`（需要在智控台开启视觉分析）。
5. **会话**：`listen start (realtime)` 后持续上传麦克风音频，收到 `stt`、`tts`、`llm` 事件。默认半双工：播报期间不上传麦克风（声卡余音约 0.4 秒也算播报中）。`--duplex` 时全双工，按回声增益判断用户是不是在插话。
6. **重连**：断线指数退避重连；收到 `config_updated` 通知会主动断开重连，让智控台的新配置生效。

智控台配置：意图识别必须选 **Function Call**，角色提示词见 `linx-client/prompts/agent-prompt.md`。

**拍照 / 视觉**：`POST <vision.url>`，multipart 字段 `question` + `file`（`camera.jpg`），请求头 `Authorization: Bearer <vision.token>`、`Device-Id`、`Client-Id`，返回 `{"response": "<分析文字>", "success": true}`。调用太密会被返回 403，所以闭眼导航只拍一张图。

## 3. MCP 工具（`linx-client/linx_client/tools.py`）

工具描述直接决定大模型什么时候调用，比如开火只在用户明确要求时调用、闲逛绝不开火。参数只用 integer / string / boolean，整数自动裁剪到 min/max。

| 工具 | 参数 | 说明 |
|---|---|---|
| `self.tank.stop` | — | 立即停车，清空队列，取消正在跑的任务；优先级最高 |
| `self.tank.move` | `direction` forward/backward，`duration_ms` 100–5000（默认 1000），`speed` 10–100（默认 80） | 直线移动 |
| `self.tank.turn` | `direction` left/right，`angle` 10–360（默认 90） | 原地转向，按 `--turn-ms-per-90` 换算时长；超过 90° 拆成几段 |
| `self.tank.barrel` | `direction` up/down，`duration_ms` 100–1500（默认 300） | 炮管抬高 / 压低（连续旋转舵机，按时长控制） |
| `self.tank.fire` | `shots` 1–3（默认 1） | 发射 |
| `self.tank.dance` | — | 原地左右扭两下，炮管上下点头 |
| `self.tank.set_persona` | `persona`：normal、grandpa 等 | 切换人格（老爷爷：限速、走走停停） |
| `self.get_device_status` | — | 车是否在线、延迟、是否刚重启；最近一次失败原因；当前动作、队列、限速、已发射数 |
| `self.tank.wander` | — | 闲逛，直到说「停」 |
| `self.macro.save` / `run` / `list` / `delete` / `record_start` / `record_stop` | 名字、步骤、重复次数 | 动作宏（语音编程）：边做边学或一句话定义，说名字就执行 |
| `self.camera.take_photo` | 问题 | 拍照并让视觉模型回答（需要 `--camera`） |
| `self.blind.map` / `self.blind.goto` | 目标、`where`（旁边 / 后面 / 左边 / 右边 / 绕一圈 / 撞倒） | 闭眼导航（需要 `--blind`） |

工具调用**立即返回「已安排」**，动作在后台队列里按顺序执行，所以大模型连续调用多个工具时会自然串成一段序列。工具出错一律转成 `isError` 结果返回，不会让连接断掉。

## 4. 控车协议

### 4.1 Wi-Fi UDP（主用）

车上程序 `firmware/car/wifi_main.py`，用 `python -m linx_client wifi-setup` 安装。依次连 `/wifi.json` 里的 2.4G 网络，都连不上就自己开热点 `CyberBrick-Tank`（192.168.4.1）。

UDP 4210，每个包一条 ASCII 指令，回一条应答；只执行白名单指令，不执行任意代码：

| 指令 | 含义 |
|---|---|
| `ping` | 回 `pong` |
| `stat` | 回 `stat up=<开机秒数> mem=<空闲内存>`，主机据此发现车中途重启过 |
| `drive <l> <r> <ms>` | 两条履带速度 -100..100（正数前进），`ms` 后看门狗自动停 |
| `turret <sp> <ms>` | 炮管舵机速度 -100..100，0 为停 |
| `fire <ms>` | 扣扳机，`ms` 后回位 |
| `halt` | 全部停下 |
| `led <r> <g> <b>` | 车灯颜色 |

- 主机端 `tank/udp.py`：每条指令等应答，超时重发。找车顺序：上次的 IP → 广播 3 轮 → 本网段逐个单播（ESP32 省电时常漏收广播）。
- TCP 8266 是维护通道：先发维护密码，之后可以无线执行代码（`car-exec`）、无线更新程序（`wifi-setup --host <IP> --code-only`）。
- 车端网络出错只记日志继续；其他意外错误先停车、写 `/wifi_err.log`、再重启。

### 4.2 USB 串口（有线调试）

`tank/serial_repl.py`：连接时 Ctrl-C 打断原厂程序，进入 raw REPL，一次性注入 `BOOTSTRAP`（定义 `drive / aim / fire / halt` 和看门狗），之后每条指令只发一行函数调用。退出后按 Core 复位键恢复原厂遥控。

### 4.3 共同语义

**时长由主机控制，车只设状态**：`drive(left, right, failsafe_ms)` 只设置输出并启动车上看门狗（`machine.Timer`），主机 sleep 到点后发 `halt`。`failsafe_ms = 时长 + 300ms`，电脑崩溃、断网或拔线后车都会自己停。

### 4.4 接线（来自车上原厂配置 `rc_config`）

| 执行器 | 端口 | 控制方式 |
|---|---|---|
| 履带 | MOTOR1 Pin4/5、MOTOR2 Pin6/7（反装） | 车上原厂驱动 `/bbl/motors.py` |
| 炮管 | SERVO1 Pin3 | 连续旋转舵机，速度 + 时长 |
| 发射扳机 | SERVO2 Pin2 | 角度舵机，150° 扣下 / 86° 松开 |

## 5. 安全设计（代码已实现）

所有入口（语音、网页、手机手柄、动作宏、闲逛和导航任务）都经过 `tank/executor.py`，不允许直接调用 backend。

1. **设备端看门狗**：每条指令到点自动停车。
2. **急停**：语音「停」、终端回车、网页急停按钮、键盘 Esc。急停不进队列，清空队列并取消任务。
3. **限速**：速度裁剪到 `--max-speed`（默认 100）。
4. **时长**：单个动作 ≤ 5 秒，队列总时长 ≤ 15 秒，超出直接拒绝。动作宏一次最多 60 秒。
5. **发射**：每次最多 3 发，间隔 1.5 秒冷却；`--no-fire` 一键锁定；提示词禁止对人或动物开火；闲逛绝不开火。
6. **故障可见**：后台动作失败会推送到网页并语音播报；空闲时每 5 秒心跳，发现车没应答或重启过会报告。
7. **测试规程**：首测架空履带，发射口朝向无人区域。

## 7. 风险与应对

| 风险 | 应对 |
|---|---|
| 外放回声触发误识别，小车自己给自己下指令 | 默认半双工；演示时戴耳机 |
| 视觉接口调用太密被限流（403） | 闭眼导航只拍一张图；403 时提示重启程序重新拿 token |
| 转向和直行距离随地面、电量变化 | `--turn-ms-per-90`、`--blind-cm-per-s` 现场校准 |
| 赛场 Wi-Fi 不稳 | 车可以连多个网络（含手机热点），都连不上会自己开热点 |
| 平台以后开始校验 token | 代码一直带着 token，届时不用改 |

## 8. 目录结构

云端模拟原型的网页通过认证后的 WebSocket 发送按键与单声道 16kHz/16 位/20ms PCM 音频，接收灵矽下行的单声道 PCM；采用半双工，当前不支持 Opus。独立 Nginx 提供 HTTPS、Basic Auth 和限流，应用层再校验密码与 Origin；后端只监听回环地址且固定 MockBackend、禁用发射。云端身份与电脑身份分开，平台下发的已知 `ws://` 地址升级为 `wss://`。真实语音、网络抖动和回声仍需实测；实车网关、指令时效/去重和车载画面未实现，不能将该接口用于真实车辆。运行方法见 [云端模拟验证](云端模拟验证.md)。
