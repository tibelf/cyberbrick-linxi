# CyberBrick Voice — 技术方案 v3：纯网页版（Android）

> 决策日期：2026-10-23。**手机浏览器本身就是灵矽设备**：手机负责听和说，网页直连灵矽平台，再由网页直接控车。不需要电脑。
> 和 v2 的关系：v2 的 `linx-client/`（Python）保留，用作参考实现、电脑上的备用方案和协议回归测试。网页版的协议、工具和安全约束都与它保持一致。
> 状态：方案阶段。

---

## 1. 前提（已实测，2026-10-23）

| 事实 | 依据 |
|---|---|
| 浏览器能直连灵矽 WebSocket：`wss://xrobo-io.qiniuapi.com/v1/ws/?device-id=<MAC>` | 实测平台只认 `device-id`（放在 URL 参数里也行），不校验 token；模拟浏览器带 Origin 请求头也没问题 |
| 浏览器能调用 OTA 接口完成激活 | `https://xrobo.qiniuapi.com/v1/ota/` 的跨域预检返回 `Access-Control-Allow-Origin: *`，自定义请求头都在允许列表里 |
| 下行音频是 PCM 16kHz/16bit/单声道 | 浏览器不需要 opus 解码 |
| 目标设备 | Android 手机 + Chrome（支持 WebUSB 和 Web Bluetooth；iPhone 两者都不支持） |

⚠️ 「不校验 token」是平台目前的行为，以后可能会变。代码里仍然要把 token 一起带上（请求头传不了，就放进 URL 参数），这样平台收紧鉴权后改动最小。

## 2. 架构

```
┌──────────────── Android Chrome（HTTPS 页面，可装成 PWA）────────────────┐
│ 麦克风 ─getUserMedia─▶ AudioWorklet 重采样 16k PCM/20ms ─┐               │       ┌───────────────┐
│ 扬声器 ◀─AudioContext 播放队列 ◀─ PCM 16k ──────────────┤  linx 会话     │  WSS  │ 灵矽平台        │
│                                                          ├─(hello/listen)─┼──────▶│ ASR→LLM(FC)→TTS│
│ UI：说话状态 · 识别文字 · 方向键 · 大号急停 · 日志         │  MCP 服务       │◀──────│                │
│                                                          │  动作队列+安全  │       └───────────────┘
│                                                          └──────┬────────┘                        │
│                              ┌──────────── TankBackend ─────────┼───────────────┐                  │
│                              │ mock      │ usb（WebUSB）         │ ble（Web BT）  │                  │
└──────────────────────────────┴───────────┴───────┬──────────────┴──────┬────────┴──────────────────┘
                                                   │ OTG 线：raw REPL     │ BLE GATT：白名单指令
                                                   ▼                      ▼
                                   CyberBrick Core（ESP32-C3）：drive / aim / fire / halt + 看门狗
```

网页按模块对应 `linx-client` 的 Python 实现，逐个移植，保持行为一致：

| 网页模块 | 对应 Python | 说明 |
|---|---|---|
| `identity` | `identity.py` | 虚拟 MAC 和 Client-Id 只存在浏览器 localStorage 里，**不进仓库**；支持导入已有身份 |
| `ota` | `ota.py` | fetch 上报，显示激活码，轮询直到绑定完成 |
| `session` | `session.py` | WebSocket、hello、listen、stt/tts/llm 事件、断线重连、收到 config_updated 后重连 |
| `audio` | `audio.py` | 采集：`getUserMedia({echoCancellation, noiseSuppression})` → AudioWorklet 降到 16k、转 int16、切成 20ms 一帧。播放：按收到的顺序排进 AudioBuffer 队列 |
| `mcp` / `tools` | `mcp.py` / `tools.py` | JSON-RPC 处理；工具名、描述和参数 schema **原样照搬**，因为智控台提示词是按这些写的 |
| `executor` | `tank/executor.py` | 动作队列；单个动作 ≤ 5s、队列总时长 ≤ 15s、限速、发射冷却；「停」不进队列 |
| `backend/*` | `tank/backend.py`、`serial_repl.py` | 统一接口：`connect / drive(l, r, failsafeMs) / aim / fire / halt / close` |

## 3. 控车：两条链路，实现同一个接口

## 3.0 更新（2026-10-24）：优先复用原厂蓝牙「模拟」通道，车上固件不用改

用户的车没有外露 USB 口，但官方 CyberBrick App 能通过蓝牙连上车。读官方开源代码 `CyberBrick_Controller_Core/src/app_rc` 后发现：

- 原厂固件的 `rc_main.py` 里有一个 `simulation_task`：每 20ms 调一次 `rc_module.rc_simulation()`，读取 **App 发来的 JSON 指令**，然后直接驱动电机和舵机。`rc_module` 是闭源的 C 模块，蓝牙通信就在它里面。
- JSON 格式（见 `parser.py` 的 `parse_simulation_*`）：`{"actuator": "MOTOR1|MOTOR2|PWM1..4|LED1|LED2|CODE", "receiver": <idx>, "data": <舵机/灯配置>, "set_value": [<事件>]}`。电机速度 = 2047 × 百分比 / 100。
- **自带看门狗**：`simulation_effect_handle` 里，收到最后一条指令 2000ms 后自动停止，并把控制权交还给遥控器（`BEHAVIOR` 权限）。所以要持续运动，就得每 < 2s 重发一次。
- `rc_module.file_transfer()`：App 用它给车写配置文件 `rc_config`。以后也许能借这条路无线部署我们自己的程序（待研究）。

**新的首选控车方式**：网页通过 Web Bluetooth 模拟官方 App，发同样的 simulation 指令。好处是车上不用刷任何东西，原厂遥控照常可用，也是无线的。
**未知**：GATT 服务和特征的 UUID、分包方式、有没有配对或加密握手、`set_value` 里的事件 ID 怎么编码。**获取办法**：在 Android 上开启「蓝牙 HCI 信息收集日志」，用官方 App 的测试功能操作电机、舵机和发射，再用 `adb bugreport` 导出 btsnoop 日志来分析；不够的话再反编译 App。

§3.1（WebUSB）因为车没有外露 USB 口，降为备选；§3.2（自写 BLE 固件）只在原厂协议走不通时才做。

### 3.1 有线：WebUSB + raw REPL（先做）

- 手机用 **USB-C OTG 线**连接 Core，手机固定在车上，正好满足课题「在车里装上灵矽」。
- Android Chrome 不支持通过 Web Serial 访问 USB 设备，所以用 Google 的 **`web-serial-polyfill`**：它基于 WebUSB 实现了 CDC-ACM 串口；电脑上的 Chrome 直接用原生 Web Serial。
- 协议**照搬** `serial_repl.py`：Ctrl-C 打断原厂程序 → Ctrl-A 进入 raw REPL → 注入 `BOOTSTRAP` → 之后每条指令一行（`drive(40,40,2300)`）。**车上固件不用改。**
- `BOOTSTRAP` 只维护一份：抽到 `shared/bootstrap.py`，Python 和网页都从这里读取，避免两边不一致。
- 风险：Core 的 USB 是 ESP32-C3 原生的 USB-Serial/JTAG（VID `0x303A`），还是外接了 CP210x/CH340 转串口芯片？polyfill 只支持标准 CDC-ACM。**这一点要在 W0 验证**（见 §6）。另外 OTG 供电时，手机会给 Core 供电，要注意电量。

### 3.2 无线：Web Bluetooth + BLE 固件（后做）

- 车上部署一个 BLE 固件 `firmware/ble_tank.py`（MicroPython `bluetooth` / `aioble`），提供一个自定义 GATT 服务：
  - `cmd` 特征（Write）：只接受**白名单指令**，例如 `D <l> <r> <ms>`、`A <angle>`、`F <ms>`、`H`。**绝不执行任意代码。**
  - `state` 特征（Notify）：每 500ms 发一次心跳和当前状态。
  - 看门狗语义和有线版一致（`machine.Timer`）。另外如果 BLE 断开，立刻 `halt()`。
- 配对口令：连接后第一条必须是 `K <口令>`，否则拒绝后续指令，防止旁边的人用手机连上你的车。
- 和原厂遥控共存：用启动模式二选一（按住某个键上电进入 BLE 模式），不覆盖原厂文件。前提是 **M0 已经备份原厂文件**。
- 风险：原厂程序本身可能就占用了 BLE 或 ESP-NOW；Web Bluetooth 首次连接必须由用户点击触发设备选择框。

## 4. 部署与开发

| 项 | 方案 |
|---|---|
| 技术栈 | Vite + TypeScript，不用 UI 框架（界面很简单）；测试用 Vitest（覆盖 executor、mcp、raw REPL 解析，移植 Python 的测试用例） |
| HTTPS 托管 | GitHub Pages（仓库是公开的，免费，自带 HTTPS），用 GitHub Actions 自动部署 |
| 开发调试 | 电脑 Chrome 打开 `localhost`（属于安全上下文，能用麦克风、Web Serial 和 Web Bluetooth），流程能完整跑通；真机调试用 `chrome://inspect` 远程调试 |
| 手机常亮 | Screen Wake Lock API；加入 PWA manifest，可以全屏启动 |
| 目录 | `web/`（网页）、`shared/bootstrap.py`（车上的驱动代码）、`firmware/`（原厂备份和 BLE 固件） |

## 5. 安全

1. 看门狗、单个动作和队列时长上限、限速、发射冷却：与 v2 一致，代码移植时保持不变。
2. 急停：说「停」，或者按屏幕上的大按钮；页面切到后台或 WebSocket 断开时自动停车。
3. **Device-Id 就是唯一凭据**：只存在手机 localStorage 里，绝不写进仓库，页面上也打码显示。仓库里已经公开的旧 Device-Id 待更换（见 HANDOFF）。
4. BLE 只接受白名单指令，并且要先验证口令。
5. 页面本身不保存任何密钥，可以放心部署在公开托管上。

## 7. 风险

| 项 | 影响 | 应对 |
|---|---|---|
| Core 不是标准 CDC-ACM，polyfill 用不了 | W3 走不通 | W0 先验证；不行就直接上 W4 蓝牙 |
| 平台开始校验 token，或者关闭 URL 参数方式 | 网页连不上灵矽 | 代码里始终带上 token；备选：一个很小的转发服务（Cloudflare Worker）帮网页补上请求头 |
| 手机外放的声音被麦克风收进去，误触发指令 | 小车自己给自己下指令 | 开启回声消除，默认半双工；演示时用蓝牙耳机 |
| Chrome 切到后台时，麦克风和 WebSocket 被挂起 | 断开连接 | 用 Wake Lock 保持前台；切到后台时自动停车 |
| OTG 供电耗电 | 续航 | 车上自带电池给 Core 供电，演示前给手机充满电 |
